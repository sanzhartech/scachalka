# Защита проекта «Scachalka» (Настольный мультимедийный менеджер загрузок)

Данный документ представляет собой полное руководство и структурированный материал для успешной защиты проекта (курсовая работа, дипломный проект или демонстрация перед комиссией).

## 1. Паспорт проекта

| Параметр | Значение |
|---|---|
| **Тема работы** | Разработка отказоустойчивого кроссплатформенного графического интерфейса для пакетной загрузки и конвертации мультимедийных данных |

## 2. Актуальность и проблематика

Консольные утилиты `yt-dlp` и `ffmpeg` признаны мировым стандартом в области анализа и загрузки мультимедиа, однако:
1. **Высокий порог входа:** Обычным пользователям трудно работать с сотнями ключей командной строки.
2. **Проблемы существующих GUI-решений:**
   - Большинство альтернатив написаны на тяжелых веб-оболочках (Electron), потребляющих гигабайты оперативной памяти.
   - Нестабильность и зависание интерфейса при длительных операциях (блокировка UI-потока).
   - Уязвимости безопасности (исполнение команд через shell с риском Command Injection).
   - «Зависание» дочерних процессов в системе при отмене загрузки пользователем.
   - Отсутствие интеллектуальных механизмов миграции музыкальных библиотек (например, Apple Music → локальная фонотека).

**Цель проекта:** Создать нативный, высокопроизводительный, надежный и архитектурно выверенный графический комплекс для операционной системы Windows, обеспечивающий пакетную загрузку, умное сопоставление треков и управление очередью с максимальным комфортом для пользователя.

## 3. Архитектурные особенности и преимущества

Проект разделен на 6 четко изолированных слоев:

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Composition Root: YtDlpGui.App (DI, Lifecycle, Global Ex)│
├──────────────────────────────┬──────────────────────────────┤
│ 2. Presentation Layer:       │ 3. Infrastructure Layer:     │
│    YtDlpGui.UI (WPF, MVVM)   │    YtDlpGui.Infrastructure   │
│    - Двуязычность (RU/EN)    │    - Запуск процессов (Tree) │
│    - Светлая/Темная тема     │    - Поиск и автоапдейт утилит│
│    - Неблокирующий UI        │    - JSON-хранилище настроек │
├──────────────────────────────┴──────────────────────────────┤
│ 4. Application Layer: YtDlpGui.Application                  │
│    - QueueCoordinator (SemaphoreSlim, ограничение потоков)   │
│    - DownloadExecutor (жизненный цикл и повторы)            │
│    - Импорт Apple Music и массовый импорт ссылок            │
├─────────────────────────────────────────────────────────────┤
│ 5. Domain / Core: YtDlpGui.Core (Чистая логика, 168 тестов) │
│    - SongMatchScorer (алгоритм нормализации и скоринга)     │
│    - ArgumentBuilder (Strategy для форматов аудио и видео)  │
│    - ProgressParser (двухуровневый отказоустойчивый парсер) │
│    - LinkParser & Normalizer (CSV / JSON / TXT)             │
├─────────────────────────────────────────────────────────────┤
│ 6. Abstractions: YtDlpGui.Abstractions                      │
│    - Контракты интерфейсов, DTO-модели, доменные энумы      │
└─────────────────────────────────────────────────────────────┘
```

### Примененные паттерны проектирования:
- **Clean Architecture & Dependency Inversion (DIP):** Все зависимости направлены внутрь. Слой Core ничего не знает о WPF или процессах Windows.
- **MVVM (Model-View-ViewModel):** Полное разделение интерфейса и логики. Связывание через Data Binding и команды (`IRelayCommand`).
- **Strategy (Стратегия):** `IArgumentBuilder` позволяет добавлять любые новые кодеки или форматы без изменения исполнительного движка.
- **Factory & Strategy:** `ILinkSource` для поддержки любых форматов импорта (CSV, JSON, TXT; легко расширяется на M3U, Spotify).

## 4. Ключевые инженерные решения (Highlight для комиссии)

### 1. Интеллектуальный алгоритм сопоставления Apple Music (`ISongMatchScorer`)
- Проблема: при экспорте трека вида «Artist - Title» прямой поиск на YouTube выдает любительские каверы, караоке, ремиксы, nightcore или видео плохого качества.
- Решение: разработан эвристический алгоритм скоринга (0–100% уверенности).
  - Сравнение названий и исполнителей с нормализацией регистра и диакритики.
  - Анализ отклонения хронометража трека.
  - Позитивные коэффициенты за официальные релизы (`Official Audio`, VEVO, топик-каналы YouTube Music).
  - Жесткие штрафы за модифицированные версии (`slowed + reverb`, `bass boosted`, `remix`, `live`, `karaoke`, `AI`).
  - Порог отсечения: некачественные совпадения отбрасываются и логируются в `failed_songs.txt`.

### 2. Безопасность выполнения процессов (Zero-Shell Execution)
- Вместо вызова `cmd.exe /c` или `powershell` используется непосредственный запуск через `ProcessStartInfo.ArgumentList`.
- Исключена возможность атаки типа Command Injection даже при вставке пользователем вредоносных символов (`;`, `&&`, `|`, кавычки).

### 3. Graceful Cancellation и контроль дерева процессов
- При отмене загрузки стандартный `process.Kill()` оставляет дочерний `ffmpeg` висеть в памяти.
- В проекте реализовано принудительное уничтожение всего дерева дочерних процессов (Process Tree) и автоматическое удаление временных файлов `.part`.

### 4. Отказоустойчивость при блокировке cookies
- Если пользователь выбрал браузер, который в данный момент запущен, база данных SQLite cookies блокируется операционной системой.
- Приложение автоматически классифицирует ошибку, перехватывает ее и запускает повторную загрузку без cookies, предотвращая сбой.

### 5. Потоковая обработка больших объемов ссылок
- Парсинг файлов с 10 000+ ссылок вынесен из графического потока в фоновые задачи. Интерфейс программы остается полностью плавным (60 FPS).

## 6. Возможные вопросы комиссии и ответы

**В: Почему выбран .NET 8 и WPF, а не кроссплатформенный .NET MAUI или Avalonia / Electron?**
> **О:** Выбор обусловлен ориентацией на максимальную производительность, минимальный размер исполняемого файла и идеальную интеграцию с ОС Windows (включая нативное оформление окон через Desktop Window Manager API). Electron требовал бы от 150 до 300 МБ ОЗУ в фоновом режиме, тогда как наше решение на WPF потребляет считанные десятки мегабайт и запускается мгновенно.

**В: Как реализована защита от зависания интерфейса при загрузке тяжелых файлов или анализе 10 000 ссылок?**
> **О:** В приложении соблюдается жесткая асинхронная модель. Все длительные операции (I/O, парсинг, запуск внешних процессов) выполняются асинхронно через пул потоков (`async/await` и `Task.Run`). Связывание с UI происходит через диспетчер и реактивное обновление свойств ViewModel, благодаря чему GUI-поток никогда не блокируется.

**В: Что произойдет, если пользователь нажмет кнопку «Отмена» во время перекодирования файла в FFmpeg?**
> **О:** Реализован механизм управления деревом процессов. Через системный механизм `taskkill /PID ... /T /F` или Job Objects закрывается не только родительский процесс yt-dlp, но и порожденный им процесс ffmpeg. После этого инфраструктурный слой удаляет временные фрагменты (`.part`). В системе не остается ни "осиротевших" процессов, ни мусорных файлов.

**В: Как работает алгоритм сопоставления треков Apple Music?**
> **О:** Алгоритм нормализует строки (убирает знаки препинания, спецсимволы, приводит регистр) и оценивает текстовое сходство (расстояния Левенштейна и Джаро-Винклера). Затем анализируется длительность трека и эвристические признаки в названии видео и названии канала. Трекам с признаками `Official Audio`, VEVO и `Topic` присваиваются повышающие баллы, а трекам со словами `slowed`, `nightcore`, `remix`, `bass boosted`, `cover` начисляются штрафные баллы. Если итоговый балл ниже порога уверенности, трек не скачивается вслепую, а записывается в отчет для пользователя.
